# Font completion: how seamless is added text?

Made by `cargo run --release -p letters-fonts --example completion_report -- core/fonts/COMPLETION_REPORT.md` on this computer, with 66 test fonts (the bundled open fonts in `vendor/fonts` and fonts installed in Windows, read in place as test subjects only).

Each test font is cut down to a subset holding only the letters of “The annual report shows revenue rose in the third quarter.”, the way a PDF embeds it. The pipeline is then asked for “Jack Ferguson mixed 42 big jazz kits by Friday, Bob said.” (scenario e: subset “Oh, le café crème à côté du théâtre? The quick brown fox jumps over a lazy dog - AND Paris.”, new text “Où êtes-vous? À la fenêtre, près du lit, déjà là.”, only its accented letters measured). Only the fonts a scenario allows can lend glyphs; the full font is used only afterwards, to measure.

- **Glyph distance**: mean (and largest) outline distance between each new glyph and the true one, both at their origin, in thousandths of the em (1 ‰ is 0.05 pt at 11 pt; 0.2 pixel at 300 dpi).
- **Advance**: mean advance-width error of the new glyphs, ‰ of the em.
- **Line SSIM / differing**: the whole new sentence drawn at 11 pt, 300 dpi with the true font and with the completed one (the subset's glyphs plus the new ones, each at its own advances, no kerning on either side), compared pixel for pixel. SSIM is averaged over the 8×8 windows that have ink; “differing” is the share of inked pixels whose coverage differs by more than 1/8. Advance errors add up along the line, so one wrong width shifts every letter after it: this is the strict 1:1 pixel test.
- **Shapes SSIM / differing**: the same, with the new glyphs set at the true advances, so only their shapes and placement within their own width count.
- **Seam**: the worse of the shapes (invisible: shapes SSIM ≥ 0.995 and ≤ 1% differing; very hard to see: ≥ 0.97 and ≤ 8%; visible on close reading: ≥ 0.93 and ≤ 18%; plainly visible otherwise) and the spacing (mean advance error ≤ 1 ‰, ≤ 4 ‰, ≤ 10 ‰, more).
